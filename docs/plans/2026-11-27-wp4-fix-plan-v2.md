## F1. numeric_match accepts off-by-one large integers (executor.py:105-120) -- CONFIRMED, worse than filed

Probe (before):
| answer | reference | now | want |
|---|---|---|---|
| 1000001 | 1000000 | 1.0 | 0.0 |
| 5000004 | 5000000 | 1.0 | 0.0 |
| 999999 | 1000000 | 1.0 | 0.0 |
| 123456789 | 123456788 | 1.0 | 0.0 |
| 1000000.5 | 1000000 | 1.0 | 0.0 |
| 18.0000001 | 18 | 1.0 | 0.0 (integer reference means an integer answer) |
| 0.333333 | 1/3 | 1.0 | 1.0 (keep: non-integer reference keeps rel_tol) |
Cause: `abs(got-ref) <= max(rel_tol*max(|got|,|ref|), 1e-9)`; at 1e6 the allowance is 1.0.

Change (executor.py, `numeric_match` only): after `ref`/`got` are parsed, if `math.isfinite(ref) and abs(ref) < 2**53 and ref.is_integer()` (this order; never `int(ref)` first, "1e999" parses to inf and int(inf) raises OverflowError) then require `abs(got-ref) <= 1e-9` (absolute). Otherwise (review r5 #1) use a capped tolerance: `max(min(rel_tol*max(|got|,|ref|), 1e-6), 1e-9)`, so rel_tol cannot grow past 1e-6 absolute at large magnitudes ("1000001.5" vs "1000000.5" must be 0.0). Docstring (r5 #8): also state that integers beyond 2**53 lose float precision and fall back to the capped tolerance (9007199254740993 vs ...992 still matches); not fixed on purpose, GSM8K is nowhere near it. One sentence, "an integer reference needs an integer match; rel_tol applies only to non-integer references". `rel_tol` signature unchanged.
Rationale: GSM8K references are integers; fractions/decimals in references (0.5, 1/3) keep tolerance.

Could break: callers of numeric_match = tests/test_scoring.py:43-70 only, plus `__init__` export and the scorer slot (fitness.py:53,97,124). No src caller hard-codes it. Existing rows checked by reading: ("18.0","18") ok (exact), ("1e5","100000") ok, ("1,234,567","1234567") ok, ("1e-3","0.001") non-integer ref, unchanged, ("-$.5","-0.5") unchanged, ("1/0","0") got=None -> 0.0 unchanged, ("18.5","18") 0.0 unchanged. Residual: integers beyond 2**53 lose float precision, so they fall to rel_tol; stated limit, GSM8K not near it.

Tests (tests/test_scoring.py, add to `test_fractions_units_commas_and_notation` table or a new `test_integer_reference_needs_exact_integer`):
- FAIL before / PASS after (expected 0.0): ("1000001","1000000"), ("5000004","5000000"), ("999999","1000000"), ("123456789","123456788"), ("1000000.5","1000000"), ("18.0000001","18")
- Also FAIL before / PASS after (r5 #1, non-integer refs): ("1000001.5","1000000.5")=0.0, ("1000000.5","1000000.4")=0.0.
- Crash guard (r5 #2): numeric_match("5","1e999") and ("1e999","1e999") return a float, no OverflowError (value not pinned beyond 0.0/1.0 type; add row ("1e999","1e999") expect 1.0 via capped path: inf-inf is nan, so assert only no exception and result in {0.0,1.0}).
- PASS before and after (guards): ("1000000","1,000,000")=1.0, ("1e6","1000000")=1.0, ("0.333333","1/3")=1.0, ("18.0","18")=1.0.
Run: `.venv/bin/python -m pytest tests/test_scoring.py -q` then full suite and `ruff check .`.

## F2. majority vote counts raw strings, scorer is numeric (fitness.py:224 per review; actual line is `_vote`, fitness.py:~122 `Counter(answers)`) -- CONFIRMED by reading

Probe: `Counter(["18","$18","18.0"]).most_common(1)` -> `[('18', 1)]`: three one-vote groups, first-seen wins. `extract_answer("Answer: $18.00")` -> `'$18.00'`, so the strings do differ in practice. Result: 2x"$18" + 1x"18.0" vs 2x"7" is decided by arrival order / tie, not value. Baseline B3/B5 is understated vs committee arms.

Change:
1. executor.py: add `numeric_key(s: str) -> Hashable`: `v = _last_number(s)`; if None return `exact_match`-style normalised string (`re.sub(r"\W+"," ",s.lower()).strip()`); if `math.isfinite(v) and abs(v) < 2**53 and v.is_integer()` return `int(v)`; else `round(v, 9)` (r5 #3: NOT `.9g`, which collapses 123456789.5 onto int 123456790 while numeric_match scores them 0.0). Int and float keys compare equal across types on purpose (r5 #4: 18 == 18.0, same hash). The key is an equivalence approximation of numeric_match: "1/3" and "0.333333333" group together (agrees with scorer); numeric_match's 1e-6 tolerance is wider than the key's 1e-9 rounding, so near-equal decimals can score alike yet vote apart (conservative; documented). Export in `__init__`.
2. fitness.py `_vote(..., vote_key=None)`, `majority_vote_detail(..., vote_key=None)`, `majority_vote(..., vote_key=None)`: keyword-only, default None = today's raw-string grouping (so all existing callers and `test_cost_is_totalled...` are bit-identical). When given, group by `vote_key(answer)`; the winner returned/scored is the FIRST raw answer of the largest group (keeps `TaskScore.answer` a real model string, so `assertIn(r.answer,{ref,"wrong"})` still holds). Tie behaviour unchanged: first-seen group wins (Counter insertion order).
   Implementation sketch: `groups: dict[key, list[str]]`; `winner = max(groups.values(), key=len)[0]` (max returns first max, so first-seen on ties, same as most_common).
3. Blank replies (r5 #7), DECISION: documented baseline caveat, not excluded. Empty/whitespace answers group under key "" and can win a vote (3 blanks of 5 -> score 0). Dropping them would be a semantic change that favors the baseline over the committee arms (which also score a blank as wrong) and is not 3 trivial lines once an all-blank fallback and tests are counted. Same as the raw path today. Docstring on `_vote` notes it. Re-decide in WP1 if blank rate is non-trivial (runner should log blank-answer count).
4. Not defaulted from the scorer on purpose (a scorer is an opaque callable; guessing numeric voting for exact_match runs would change semantics). Benchmark passes `vote_key=numeric_key` explicitly together with `scorer=numeric_match` (see F3).

Could break: callers of majority_vote / _detail: examples/run_mock.py:26 (positional ev,i,5; unaffected), tests/test_scoring.py:227-278 (no vote_key; unchanged path), `__init__` exports. Cost totalling untouched (`total += r.cost` stays in call order). Collision risk: "7" vs "7 apples" now one vote (intended); "3:30" vs "30" collide (existing documented limit of _last_number).

Tests (new, in MajorityVoteSamples; scripted backend `class Scripted: complete(prompt, model, sample) -> Response(text, 1, 1, 0.0)` returning `["Answer: $18","Answer: 7","Answer: 18.0","Answer: 7","Answer: $18"][sample]`... concretely use replies by sample: s0 "Answer: $18", s1 "Answer: 7", s2 "Answer: $18.00", s3 "Answer: 7", s4 "Answer: 18.0", k=5, task ref "18", scorer=numeric_match):

Before (raw strings): groups "$18","7"x2,"$18.00","18.0" -> winner "7", score 0.0. (The `vote_key` kwarg does not exist yet, so the test fails with TypeError before; also add the no-key assertion `score == 0.0` pinning the old default, PASS both sides.)
