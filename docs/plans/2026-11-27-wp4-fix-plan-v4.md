# WP4 fix plan v4 (amended per Codex r8): one canonical number (supersedes v3, which Codex r7 rated NO-GO)

Repo ~/evoharness, branch plan/benchmark-mixed-committee, base 6a47a3b. Amended 2026-11-27 for r8 (GO WITH CHANGES); built from this version, see Review trail.
Prototype + probe: /tmp/probe_v4.py on omarchy (copy at /tmp/claude-1000/probe_v4.py), run in .venv. All numbers below come from that run.

## Why v3 failed
`numeric_match` is asymmetric (integer ref uses abs 1e-9, decimal ref uses capped rel_tol) and non-transitive (tolerance bands chain). A relation like that cannot be a partition, so no `vote_key` can agree with it (r7 P1). The fix is to stop comparing with a tolerance and compare one canonical form with `==`.

## Design (approved by Ryan)
`canonical_number(text) -> Hashable | None` in executor.py, next to `_last_number` (which it replaces).

1. Find the LAST `_NUMBER` match (existing regex and rules unchanged: commas, simple and mixed fractions, sci notation, `$`, unicode minus, sign only at number start).
2. Integer text (digits and commas only, no `.`/exponent): `int(...)` directly. Exact, no 2**53 limit.
3. Everything else (decimal, sci, fraction, mixed): exact `Fraction` (via `Decimal` for decimal/sci text), then `n = round(q * 10**D)` (exact half-even on Fraction, no float), D = 6. If `n % 10**D == 0` return `n // 10**D` as `int` (so 18.000000 -> 18, "-0.0000004" -> 0, no negative zero); else `Fraction(n, 10**D)` (auto-normalized, hashable).
4. Size policy (r8 P1/P2), ONE policy for integer, decimal, scientific and fraction spellings:
   - Input-size limit: every digit run (commas removed) has at most 309 digits: integer, whole, fraction part, coefficient integer and fraction parts, numerator, denominator, mixed whole/numerator/denominator, and the exponent digits. Checked on the matched strings BEFORE any `int`, `Decimal`, `Fraction` or `10**e` is built, so `"1." + "2"*100000` and `"1e" + "9"*100000` return None without allocation. This also covers the `int()` 4300-digit ValueError.
   - Magnitude limit: the rounded value satisfies `|value| < 10**309` (decimal `adjusted() <= 308`). Scientific text is judged by `coefficient.adjusted() + exponent` BEFORE conversion: `> 308` is None; `< -7` is exactly 0 (a nonzero value below 1e-7 rounds to 0), without building `10**e`; a zero coefficient is 0 whatever the exponent. Otherwise `Fraction(Decimal) * Fraction(10)**e`, exact (never `scaleb`: default context precision is 28).
   - The limit is on representation-independent value, not on float range: `1e308`, `"1"+"0"*308`, `10e307`, `0.1e309`, `"1"+"0"*308+"/1"` all canonicalize to the same int; `1e309`, the 310-digit integer, `10e308`, `"1"+"0"*309+"/1"` are all None. Mixed fractions and a value that ROUNDS up to 10**309 (`"9"*309+".9999999"`) are caught by the post-rounding magnitude check. The old float boundary (1.797e308) is not kept: `9e308` was inf in the old code and is a valid number now.
   - Also None: no number; denominator 0.
5. The LAST number token decides. If it is invalid (`1/0`, `1e309`) the result is None; it does not fall back to an earlier number (old code did `continue`; `"5 or 1/0"` was 5, see "Behavior changes").

### Choice of D = 6 (policy, stated honestly)
D=6 is a six-place bucket policy, NOT "the same resolution as before". Old decimal tolerance was magnitude-dependent (`rel_tol*max`, floor 1e-9, cap 1e-6), so near 0.1 it was ~1e-7. Now: `0.1` MATCHES `0.1000004` (old: no), and `0.0000004` MATCHES `-0.0000004` (old: no; they share the zero bucket, by design, no negative zero). `0.333333` equals `1/3` (the r6 regression, probed). D=9 would break that; D<=4 would merge 0.3333 and 0.33333. Integers are never rounded. Boundary splits (below) hit fractions such as `1/3` regardless of how many places the reference has.

## The guarantee
Equivalence: for any two strings a, b whose canonicals are both non-None, `numeric_match(a,b) == 1.0  <=>  numeric_key(a) == numeric_key(b)`. Both are `==` on one value, so the relation is reflexive, symmetric and transitive on numeric answers by construction. `match == 1.0 => key equal` holds for ALL strings.
Universal statement (r8 P2; replaces the earlier "winner is correct iff ..."): **for any fixed reference, all answers that share a key receive the same score.** It does NOT say the winning group is the reference's group: identical blank or invalid answers share a key and score 0 against every reference, and an invalid reference (`1/0`, `1e309`, `""`, `"$"`, text) scores every winner 0. Tests: blank-majority (`["", "", "5"]` ref 5 -> winner "", 0.0) and invalid-reference (`["5","5","7"]` refs `1/0`, `1e999`, `""`, `"$"` -> "5", 0.0).

## The tradeoff: rounding-boundary splits
Two values within 1e-6 can land in different buckets. Concrete (probed): `0.3333334` -> 0.333333, `0.3333335` -> 0.333334 (half-even: 333333.5 -> 333334). They are 1e-7 apart but do not match. Likewise `1/3` (0.333333) does not match `0.3333335` (0.333334). Old code matched these. Accepted by Ryan: a hard boundary is the price of an exact equivalence relation. Mitigation: none in code; documented in the docstring. At D=6 this only matters for answers written to more than 6 places that straddle a half-unit, rare for benchmark references (GSM8K is integers).

## Behavior changes vs current (every existing test row that flips, from probe)
Of the 62 rows in tests/test_scoring.py NumericMatch/NumericVote, exactly 2 flip, plus 1 key row:
1. `numeric_match("18.0000001","18")` 0.0 -> 1.0 (test_integer_reference_needs_exact_integer). 18.0000001 rounds to 18 at D=6. Old rule was an integer-ref abs 1e-9 special case; that asymmetry is exactly what r7 flagged. Change test: move to expected 1.0 and add `("18.000001","18") -> 0.0` and `("18.0000004","18") -> 1.0` to pin the boundary. Integer rows 1000001/1000000, 5000004, 999999, 123456789/123456788, 1000000.5 vs 1000000 all stay 0.0 (probed).
2. `numeric_match("Paris","paris")` 1.0 -> 0.0 (test_falls_back_to_exact_match...). Per Ryan's rule, no number -> 0.0, which is also what makes `""` vs `"$"` 0.0 (old: 1.0 via exact_match on punctuation-only; r7 P3). Needs Ryan's OK: text benchmarks must use `exact_match` as scorer, not `numeric_match`. Change test to assert 0.0 for both Paris pairs and that `exact_match` still returns 1.0. `Lyon`/`Paris` stays 0.0.
3. `numeric_key("Paris") == numeric_key("paris")` (test_numeric_key_rows) -> now unequal (key is stripped raw text). Move to the not-equal list; add `("Paris","Paris ")` equal.
Unchanged (probed): `1/2`=0.5, `2 1/2`=2.5, `3/4 cup`, `18 m^2`, `1,2`!=12, `12,34`!=1234, `1e-3`=0.001, `1e5`, unicode minus, `-$.5`, `1/0` vs `0` 0.0, `50%`=50, `between 3-5` = 5, `1000000.5` vs `1000000.4` 0.0, `1000001.5` vs `1000000.5` 0.0, `0.333333`=`1/3`, `1/3` key = `0.333333333` key.
Not in tests, but behavior changes (document in docstring/CHANGELOG line): (a) non-integer refs lose the 1e-6 relative band: two decimals 8e-7 apart now match only if same bucket; (b) NOT a change (r8 correction): old `numeric_match("1e999","1e999")` already returned 0.0 (inf-inf is NaN); reflexivity for out-of-range numbers is intentionally not claimed (r7 P3), their keys group by raw text so duplicate `1e999` replies still vote together. The real range change is that values between 1.797e308 and 1e309 are accepted exactly where the old float code overflowed; (c) `"5 or 1/0"` is None (last token invalid) where old code returned 5; (d) integers above 2**53 now exact: `9007199254740993` != `9007199254740992` (old: equal); (e) `rel_tol` kwarg removed from `numeric_match`.
`1e999 -> None -> 0.0` against any reference (unchanged); `"" vs "$"` -> 0.0; `""` as an answer never matches.

## Supported grammar and inherited parse defects (r8 P2: documented and pinned, NOT fixed here)
The `_NUMBER` regex is unchanged, so its defects are inherited, not v4 regressions. They are documented in the `canonical_number` docstring and pinned in `test_supported_grammar_pins_known_defects` so a later fix is a deliberate test edit: `.5e-3` reads 3 (should be 0.0005); `.5e3` reads 0.5 (should be 500); `1/-2` reads -2; `1,234 1/2` reads 0.5 (should be 1234.5); `1,2` reads 2 and `12,34` reads 34 (a bad comma group splits into two numbers; `1,2 != 12` alone proved little). Other pins: `50%`=50, `3:30`=30, `$18 for 3 days`=3, `between 3-5`=5, `18 m^2`=18. Follow-up: Taskmaster task 17 "Fix inherited numeric parse defects" (pending). Signed mixed fractions: `-2 1/2` -> -5/2 and `-0 1/2` -> -1/2 (sign applies to the whole value; correct under v4 inside the canonical code, no regex change), tested.
