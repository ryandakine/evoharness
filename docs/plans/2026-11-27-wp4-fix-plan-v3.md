# WP4 fix plan v3: vote grouping must use the scorer's equivalence

Branch plan/benchmark-mixed-committee, base HEAD 6a47a3b. Plan only; no source edits made.
Trigger: Codex code review r6 (9997a13), finding P2. Opus rated this LOW in v2 (numeric_key caveat: key rounds to 9 dp, scorer tolerance is 1e-6). Codex is right that the gap is reachable with ordinary answers, not only exotic ones. Decision: fix, small.

## Verified facts (venv probes, laptop .venv)
- numeric_match("0.333333","1/3") == 1.0 and "0.3333333" vs "1/3" == 1.0 and "0.333333" vs "0.3333333" == 1.0 (both argument orders). numeric_key equal for none of these (all three keys differ). 
- Codex example [7, 1/3, 7, 0.333333, 0.3333333], ref "1/3": with vote_key=numeric_key the groups are 7x2 and three singletons, so "7" wins, score 0.0. Three of five replies are scorer-correct.
- numeric_match is NOT transitive: "1.0000000"~"1.0000009" =1, "1.0000009"~"1.0000018" =1, "1.0000000"~"1.0000018" =0.
- Blanks: numeric_match("","")=1.0, ("", "x")=0.0, ("7","")=0.0, ("","7")=0.0 (blank as reference falls to exact_match). So a blank only ever matches another blank. Integers: "18" vs "18.0" =1, "18" vs "18.5" =0 in both orders.
- Callers of numeric_key/vote_key: only tests/test_scoring.py (NumericVote, test_numeric_key_rows, one "1e999" call in the scorer test) and __init__ exports; v2 plan text says the runner will call vote_key=numeric_key (runner not yet written). examples/run_mock.py calls majority_vote positionally, no key.

## Options
A (picked). Add `vote_match: Callable[[str, str], float] | None = None` to _vote / majority_vote / majority_vote_detail. Greedy clustering: for each answer in sample order, join the first existing group whose representative (its first member) satisfies `vote_match(answer, rep) >= 0.5`... use truthiness: `vote_match(a, rep) == 1.0`; else open a new group. Winner = first raw answer of the largest group; ties go to the first-created group (max over insertion-ordered list returns the first max). Pass `vote_match=numeric_match` and the vote uses literally the scorer function, so grouping and scoring cannot drift apart.
B (rejected). Keep keys, make numeric_key coarser (quantise to ~6 significant digits). Still a hash-bucket boundary: 0.3333334 and 0.3333335 can straddle a bucket while scoring alike; the bug just moves to a rarer input, and the key must be re-derived whenever numeric_match's tolerance rule changes (the exact drift that caused this finding).

## Design details (A)
- vote_key and vote_match are mutually exclusive: both set -> ValueError("pass vote_key or vote_match, not both"). Default (both None) stays raw-string Counter path, bit-identical.
- Matching direction: `vote_match(answer, rep)`, rep plays "reference" (the integer-reference strictness applies to the rep). Probed symmetric on every row above; asymmetry can only appear at the integer 1e-9 edge. Documented, not engineered around.
- Non-transitivity / order dependence: groups depend on arrival order (chain example: order [a,b,c] -> {a,b},{c}; order [b,a,c] -> {a,b,c}). Anchoring on the first member (not the latest) bounds drift: every member is within tolerance of the rep, so no unbounded chaining. Only matters for answers differing by ~1e-6 relative; irrelevant for integer GSM8K-style answers. Samples arrive in fixed sample order, so a run is deterministic. Note it in the docstring; do not add sorting.
- Cost O(k * groups) scorer calls per task, no model calls; k is 3-9. Token/cost accumulation loop untouched (grouping happens after it).
- Winner stays a real raw answer string (rep = first member) so TaskScore.answer is unchanged in kind.
- Blanks: unchanged policy (v2 caveat 3): blanks group together via exact_match fallback, never with numbers, and can still win.
- numeric_key: KEEP exported (public name, existing tests, harmless), add docstring line "Prefer vote_match=numeric_match: this key is an approximation and splits answers the scorer accepts (e.g. 0.333333 vs 1/3)." Do not delete in this fix (separate removal after the runner lands; surgical change). The v2 benchmark instruction changes to `vote_match=numeric_match`; the runner's startup assert (ev.scorer is numeric_match) should also assert the vote is vote_match=numeric_match, and the results header records `vote_match` name.

2. executor.py: docstring note on numeric_key only (no behaviour change).

## What could break
- Existing callers (run_mock.py positional, tests with no key): untouched path, identical.
- Anyone passing vote_key: unchanged behaviour.
- Passing a scorer-like callable that returns 0/1 floats: fine; a callable returning bool also fine (== 1.0 / truthy; use `bool(match(a, rep))`-style truthiness, and numeric_match returns 0.0/1.0 so same).
- Slower for large k with many distinct answers: bounded by k^2/2 scorer calls, trivial.
- Wrong pairing: using vote_match=exact_match with numeric scorer is the caller's choice; no default derivation from the scorer (v2 decision 4 stands).
